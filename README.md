# mind-trace

## 1. Проблема

В процессе обучения человек получает и фиксирует большое количество информации, однако сохранение материала в виде конспектов не обеспечивает его долговременного запоминания.

Основные проблемы:

- **Забывание информации.** Без регулярного повторения человеку становится сложнее самостоятельно воспроизводить изученный материал.
- **Пассивное обучение.** Перечитывание конспекта не требует обязательного воспроизведения знаний по памяти.
- **Недостаток обратной связи.** При самостоятельном обучении трудно объективно определить полноту и правильность понимания темы.
- **Сложность планирования повторений.** Пользователю необходимо самостоятельно контролировать сроки и периодичность возвращения к материалу.
- **Трудности устного объяснения.** Человек может узнавать изученную информацию, но испытывать затруднения при её самостоятельном объяснении.
- **Низкое качество исходных материалов.** Конспекты могут содержать ошибки, неоднозначности или недостаточно раскрытые понятия.

## 2. Цель

Создать приложение, которое помогает пользователю закреплять самостоятельно изученную информацию с помощью активного воспроизведения, автоматизированного оценивания знаний и интервального повторения.

Дополнительная цель — развитие способности самостоятельно и последовательно объяснять изученный материал.

## 3. Предлагаемое решение

Пользователь создаёт текстовый конспект, который служит основой для проверки знаний.

ИИ анализирует содержание конспекта, определяет возможность оценивания по нему и формирует проверочный контекст.

Пользователь воспроизводит изученный материал устно или, при поддержке соответствующего режима, текстом.

Голосовой ответ преобразуется в текст микросервисом транскрибации.

ИИ оценивает соответствие ответа проверочному контексту и возвращает результат в процентах, а также сведения о недостаточно раскрытых аспектах.

Backend использует результат оценивания для изменения расписания последующих повторений.

В перспективе приложение также предоставляет проверку достоверности конспектов через внешние источники, предложения по исправлению ошибок и интерактивный диалог с ИИ-экзаменатором.

## MVP — лабораторная работа №1

### 1. Назначение и границы MVP

MVP для лабораторной работы №1 («Серверная часть») реализует законченный цикл: **создание текстового конспекта → анализ его достаточности и формирование проверочного контекста с помощью LLM → составление расписания → голосовой ответ и транскрибация → оценивание ответа LLM → корректировка расписания на backend**.

Конспект рассматривается как единая единица повторения. В учебной версии используется одно локальное пространство данных без регистрации пользователей и графического интерфейса; работа проверяется через REST API. Вместо доставки push/email-уведомлений API предоставляет актуальное расписание и список повторений, срок которых наступил.

**Технологии:** Kotlin/Ktor (основной backend — модульный монолит), PostgreSQL (постоянное хранение), внешний LLM API (анализ и оценивание), отдельный Python-сервис (только транскрибация аудио), Docker Compose (запуск).

### 2. Функциональные требования

#### 2.1. Конспекты и проверочный контекст

| ID | Требование |

|---|---|

| FR-M01 | Система должна позволять создать текстовый конспект с названием и содержимым и получить сохранённые конспекты через API. |

| FR-M02 | Система должна сохранять конспекты в PostgreSQL. |

| FR-M03 | Система должна передавать конспект в LLM для анализа достаточности информации для проверки знаний. |

| FR-M04 | Если информации недостаточно, система должна сообщать об этом и указывать причину; расписание для такого конспекта не создаётся. |

| FR-M05 | Если информации достаточно, система должна получать от LLM проверочный контекст с основными понятиями и аспектами и сохранять его вместе с конспектом. |

#### 2.2. Повторение и оценивание

| ID | Требование |

|---|---|

| FR-M06 | Система должна принимать аудиозапись ответа по выбранному конспекту. |

| FR-M07 | Backend должен передавать аудио в Python-сервис транскрибации и получать текст ответа. |

| FR-M08 | Система должна автоматически передавать транскрипцию и проверочный контекст в LLM, без предварительного просмотра или редактирования транскрипции пользователем. |

| FR-M09 | LLM должна возвращать оценку от 0 до 100% и краткое объяснение с указанием основных пропусков или ошибок. |

| FR-M10 | Система должна сохранять текст ответа, оценку, объяснение и дату проверки с привязкой к конспекту и возвращать результат через API. |

#### 2.3. Расписание повторений

| ID | Требование |

|---|---|

| FR-M11 | После формирования проверочного контекста система должна создавать и сохранять первоначальное расписание повторений. |

| FR-M12 | Система должна предоставлять через API актуальные даты и список повторений, срок которых наступил или был просрочен. |

| FR-M13 | Система должна определять число дней просрочки и переносить оставшиеся даты на соответствующее количество дней. |

| FR-M14 | После оценивания система должна корректировать расписание согласно категории результата: 0–49%, 50–79% или 80–100%. |

| FR-M15 | Система должна сохранять пересчитанное расписание и возвращать дату следующего повторения. |

### 3. Нефункциональные требования

#### 3.1. Архитектура

| ID | Требование |

|---|---|

| NFR-M01 | Основной backend должен быть модульным монолитом с разделением ответственности между конспектами, оцениванием и расписанием. |

| NFR-M02 | Бизнес-логика должна быть отделена от HTTP-обработчиков и работы с PostgreSQL. |

| NFR-M03 | Доступ к БД, LLM и транскрибации должен осуществляться через интерфейсы, чтобы заменять реализации без переписывания бизнес-правил. |

| NFR-M04 | Расчёт дат и применение порогов оценивания должны выполняться на backend, независимо от LLM и способа предоставления API. |

#### 3.2. API, данные и надёжность

| ID | Требование |

|---|---|

| NFR-M05 | REST API должно валидировать входные данные, возвращать соответствующие HTTP-статусы и единообразные сообщения об ошибках. |

| NFR-M06 | Конспекты, контекст, оценки и расписания должны постоянно храниться в PostgreSQL, а схема — изменяться миграциями. |

| NFR-M07 | Сохранение оценки и изменение расписания должны выполняться атомарно; повторный или конкурентный запрос не должен приводить к двойному завершению одного повторения. |

| NFR-M08 | При ошибке LLM или транскрибации система должна возвращать техническую ошибку, не изменяя расписание и не записывая фиктивную оценку. |

| NFR-M09 | Внешние вызовы должны иметь тайм-ауты; их ожидание не должно блокировать независимые HTTP-запросы. |

| NFR-M10 | Исходное аудио не должно сохраняться на постоянной основе; ключи API и параметры окружения должны находиться вне исходного кода. |

#### 3.3. Запуск и проверяемость

| ID | Требование |

|---|---|

| NFR-M11 | Backend, PostgreSQL и сервис транскрибации должны воспроизводимо запускаться через Docker Compose. |

| NFR-M12 | Система должна регистрировать основные операции и технические ошибки без логирования секретов или полного содержимого ответов. |

| NFR-M13 | Основные правила пересчёта расписания должны быть покрыты модульными тестами; критические сценарии API и хранения данных — интеграционными тестами. |

| NFR-M14 | Рабочие интеграции должны использовать реальные сервисы и БД: заглушки и моки допускаются в тестах, но не вместо реализации MVP. |

### 4. Бизнес-правила

#### 4.1. Конспект и оценивание

**BR-M01.** Единица повторения — целый конспект; проверочный контекст строится только из его содержания. Внешняя проверка фактов не выполняется.

**BR-M02.** Для конспекта, который LLM признала недостаточным, проверка знаний и создание расписания недоступны.

**BR-M03.** Ответ оценивается по смыслу, а не по дословному совпадению. Результат — целое число от 0 до 100 и краткое обоснование; это приблизительная оценка LLM, а не точное измерение знаний.

**BR-M04.** Техническая ошибка распознавания речи или LLM не считается ошибкой пользователя в знаниях.

#### 4.2. Расписание

**BR-M05.** Для MVP используется фиксированная последовательность дат **через 1, 3, 7, 14 и 30 дней** от создания готового к проверке конспекта. Значения могут быть вынесены в конфигурацию.

**BR-M06.** Повторение выполняется для наступившей или просроченной даты; досрочные проверки в MVP не предусмотрены.

**BR-M07.** Если повторение выполнено позже назначенной даты, оставшиеся невыполненные даты сначала сдвигаются на число календарных дней просрочки. Затем применяется правило по оценке.

**BR-M08.** Категории оценки и действия:

| Оценка | Категория | Изменение расписания |

|---|---|---|

| 0–49% | Слабое усвоение | Заменить оставшиеся даты новой последовательностью от фактического дня проверки; первое повторение — на следующий день. |

| 50–79% | Частичное усвоение | Добавить повторение через 2 дня после проверки, сохранив остальные сдвинутые даты; совпадающие даты не дублировать. |

| 80–100% | Уверенное усвоение | Оставить остальные даты после учёта просрочки. |

**BR-M09.** Выполненные повторения и история оценок не изменяются при пересчёте будущих дат. Одно повторение может быть завершено только один раз.

**BR-M10.** Список повторений, требующих выполнения, формируется только по актуальному расписанию. Просроченное повторение остаётся в этом списке до завершения.

### 5. Основные варианты использования

#### UC-01. Создать конспект

**Актор:** пользователь. **Предусловие:** нет.

1. Пользователь отправляет название и текст конспекта.

2. Система проверяет входные данные и сохраняет конспект.

3. LLM анализирует его достаточность и, если данных достаточно, формирует проверочный контекст.

4. Система сохраняет контекст, создаёт расписание и возвращает сведения о конспекте.

**Альтернатива:** данных недостаточно — система возвращает причину, расписание не создаётся.

#### UC-02. Посмотреть запланированные повторения

**Актор:** пользователь. **Предусловие:** существует хотя бы один конспект с готовым проверочным контекстом.

1. Пользователь запрашивает расписание или список повторений, требующих выполнения.

2. Система получает актуальные даты из БД.

3. Система возвращает запланированные и просроченные повторения.

#### UC-03. Пройти повторение и получить оценку

**Актор:** пользователь; внешние участники — Python-сервис транскрибации и LLM. **Предусловие:** для конспекта наступила дата повторения.

1. Пользователь отправляет аудиоответ для выбранного повторения.

2. Система транскрибирует аудио и передаёт текст ответа с проверочным контекстом в LLM.

3. LLM возвращает процентную оценку и краткое объяснение.

4. Backend учитывает просрочку и оценку, рассчитывает новое расписание.

5. Система атомарно сохраняет результат проверки и изменённое расписание.

6. Пользователь получает оценку, объяснение и дату следующего повторения.

**Альтернатива:** транскрибация или оценивание завершились технической ошибкой — проверка не засчитывается, расписание не меняется.

### 6. Что не входит в MVP

Регистрация и авторизация; графический интерфейс; редактирование конспектов и версионирование; проверка достоверности материалов по внешним источникам; автоматическое исправление конспектов; просмотр транскрипции до оценивания; многошаговый диалог; анализ акустических характеристик речи; отдельное расписание для каждого понятия; персонализированная модель забывания; фактическая отправка push/email/Telegram-уведомлений.
